## Архитектура: списание баланса

### Хранение

* `users.balance` — текущий баланс пользователя (`bigint`, минимальные единицы валюты).
* `balance_logs` — история операций: `user_id`, `action`, `amount`, `idempotency_key`, `timestamp`.

Суммы хранятся как `bigint`, а не `float` из-за необходимости точных вычислений. На границе API значения конвертируются в `string`: `JSON.stringify` не сериализует `BigInt`, а использование `Number` может привести к потере точности.

### Пересчёт баланса

После каждого списания баланс пересчитывается через `SUM(amount)` по всей истории (`recomputeBalance()`).

### Атомарность

Списание выполняется в рамках транзакции БД:

1. `SELECT ... FOR UPDATE` блокирует строку пользователя.
2. После получения блокировки проверяется `balance >= amount`.
3. Добавляется запись в `balance_logs`.
4. Выполняется `recomputeBalance()`.
5. Обновляется `users.balance`.

`FOR UPDATE` необходим, поскольку проверка баланса и его обновление выполняются отдельными операциями.

### Идемпотентность

`idempotency_key` обязателен и используется для защиты от повторных списаний при ретраях клиента.

В БД установлен уникальный constraint на `idempotency_key`.

При повторном запросе:

* если `user_id` и `amount` совпадают — возвращается результат предыдущей операции;
* если данные отличаются — возвращается `409 Conflict`.

При гонке на вставке и получении `unique_violation (23505)` транзакция ретраится целиком. Отдельные запросы внутри уже aborted-транзакции не повторяются.
